# Define the Safe Repair authority boundary

Some lifecycle inconsistencies are not user decisions. An existing installation whose Project is now a Git repository, an absent generated output, a missing Installation Marker, or a damaged repository-local exclusion section were all surfaced as Blockers that exposed internal bookkeeping and asked the user to restore an unspecified Installation State backup. Other conditions genuinely require the user: tracked generated paths, modified user-managed material, unreadable Installation State, and unprovable Git topology lack evidence or authority for automatic action. The lifecycle must distinguish these authority boundaries instead of treating every inconsistency as equivalent (spec #345).

The accepted boundary:

- A **Safe Repair** is the deterministic restoration of Agent Profile Kit-owned output or lifecycle metadata from existing durable ownership evidence when no user-managed bytes or repository ownership change. It uses the ordinary `status` → `apply` lifecycle: `status` performs no writes and presents the repair as non-blocking pending work; `apply` reacquires and rechecks every required proof, publishes the repair through the existing lifecycle lock, transaction, rollback, and fresh post-commit verification, and reports the outcome like any other pending work.
- Safe Repair eligibility is **one exhaustive typed boundary**: every supported repair class — absent generated output, missing Installation Marker, missing repository-local exclusion section (including during retirement when the complete post-retirement union is proven), a provably missing Repository Exclusion Contribution, stale contribution entries at an unchanged proven target, and a contribution whose target moved between two proven targets — constructs its typed repair at its actual decision site and is classified through that boundary. Adding a class requires extending the boundary, so a repair can never surface through an ad-hoc inline branch. Each class keeps its existing evidence and presentation seam.
- Eligibility always requires independently proven live boundaries — an active Installation Receipt, a Marker whose identity matches, hash-proven owned roots, a live Project, untracked destinations, and a provable Git target — and the receipt must prove the exact write set. If any proof is absent, unsafe, unreadable, ambiguous, or would change user-managed bytes or repository ownership, the condition remains a Blocker and no write occurs.
- Surviving generated bytes are never an alternate ownership source. Agent Profile Kit does not reconstruct Installation State from generated output, silently adopt matching unowned output, overwrite drift, or automatically untrack repository paths.
- There is no general repair command. Concise output names the affected Project scope and resulting repair without teaching repository-exclusion internals; verbose and JSON retain the exact repair evidence.

The missing Repository Exclusion Contribution was the first condition delivered under this boundary through its own exhaustive class: when the proofs above hold and the target's owned section is absent or already contains exactly the recorded union plus the proven contribution, `status` classifies it as non-blocking pending work and `apply` records the contribution in the active receipt and publishes the resulting union through the ordinary transaction.

Stale contribution entries at an unchanged, proven Git target are the second delivered class (spec #345, SRC-004), deliberately narrowing this record's original rule that every entry-set mismatch remains a Blocker. When the same proofs hold — an active receipt, a present identity-matching Marker with hash-proven owned roots, an otherwise-current desired write set, and the same live Git target the receipt already records — and the receipt's recorded entries differ from the entries its owned outputs derive, the receipts prove one exact replacement: `status` classifies the correction as non-blocking pending work and `apply` replaces only the proven installation's entries through the same contribution pass and transaction, preserving every other contribution and unrelated byte. The target's live section must still match the recorded union exactly, so the replacement never disturbs unprovable bytes. Requiring the otherwise-current desired write set keeps one proof per published write: if the desired source, Profile, Host set, or output set is changing, the stale contribution stays blocking rather than showing evidence for one replacement and applying another through an ordinary update.

A contribution whose Repository Exclusion Contribution target changed while the Project path stayed is the third delivered class (spec #345, SRC-005), narrowing the same original rule for movement between Git targets. When the shared proofs hold — an active receipt, a present identity-matching Marker with hash-proven owned roots, an otherwise-current desired write set, and two independently provable targets — the receipts prove one exact two-target transition. The old target derives only from the active receipt and must independently pass path, owned-section, and exact recorded-union proof; the new target derives from live Git topology and must independently pass its own proof (path safety, then an owned section that is absent or exactly the recorded union there). `status` classifies the move as non-blocking pending work naming both targets, and `apply` removes the recorded entries at the old target and publishes the re-derived entries at the new target through the same single contribution pass and transaction, preserving every other contribution and unrelated byte. A combined condition without one exact two-target result — an unprovable, missing, malformed, unsafe, or ambiguous old or new target — stays a Blocker and causes no writes. Whole-Project relocations, where the exclusion file physically moves with the Project, remain the ordinary lifecycle path and are unaffected.

A missing repository-local exclusion section, exclusion file, or safe Git exclusion parent during intentional-deletion retirement is the fourth delivered class (spec #345, SRC-006), narrowing this record's original rule that retirement required the recorded section to be present. Intentional deletion does not authorize reconstruction of a missing contribution: when the retiring installation's recorded contribution passes the retiring-ownership gates and the active receipts and provable live target prove the complete post-retirement union through one shared typed decision, `status` classifies the retirement as non-blocking pending work and performs no writes, and `apply` publishes the exact post-retirement union — removing the Agent Profile Kit section when the union is empty, and creating the exclusion file or its safe parent only when the union requires it — and retires the receipt through the existing atomic retirement transaction, which remains the sole writer. Publication failure rolls back repository-local changes and leaves the retirement retryable. A malformed or unsafe target, an unprovable post-retirement union, or a missing authoritative contribution remains a Blocker and causes no writes.

Wrong targets, malformed or unsafe retirement-target exclusion bytes, an unprovable post-retirement union, a missing authoritative contribution, unprovable or unreadable exclusion bytes, missing identity proof, unsafe paths, and stale desired write sets remain Blockers and cause no writes.

The maintained glossary (`CONTEXT.md`) owns the canonical Safe Repair definition; this record owns the decision and its rationale.

### Amendment: eligibility requires identity-proven roots, not hash-proven roots

Issue #363 narrowed this record's requirement that Safe Repair eligibility always includes "hash-proven owned roots". Aggregate-hash equality is freshness evidence, not an authority requirement (see the ADR-0019 amendment): an active Installation Receipt plus an identity-matching Marker at safe paths grants authority over the recorded generated output roots whether or not their current bytes are fresh.

Two consequences:

- Every Safe Repair class evaluates its shared proofs against identity-proven roots. Proven-root drift (changed bytes, modes, missing or unexpected members) no longer makes a candidate ineligible, and the ordinary refresh of that drift proceeds as non-blocking pending work in the same `apply` run.
- The missing-Installation-Marker repair is the deliberate exception: a missing Marker leaves no identity proof at the Project, so its independent proofs still require every remaining owned output to be present and hash-current. Drift must not substitute for missing identity proof.

Residual ownership Blockers remain provenance-neutral: they state only what their evidence proves and never assert a user edit or prescribe moving a change into the Workspace unless that provenance is actually known.
