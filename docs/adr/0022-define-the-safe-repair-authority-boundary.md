# Define the Safe Repair authority boundary

Some lifecycle inconsistencies are not user decisions. An existing installation whose Project is now a Git repository, an absent generated output, a missing Installation Marker, or a damaged repository-local exclusion section were all surfaced as Blockers that exposed internal bookkeeping and asked the user to restore an unspecified Installation State backup. Other conditions genuinely require the user: tracked generated paths, modified user-managed material, unreadable Installation State, and unprovable Git topology lack evidence or authority for automatic action. The lifecycle must distinguish these authority boundaries instead of treating every inconsistency as equivalent (spec #345).

The accepted boundary:

- A **Safe Repair** is the deterministic restoration of Agent Profile Kit-owned output or lifecycle metadata from existing durable ownership evidence when no user-managed bytes or repository ownership change. It uses the ordinary `status` → `apply` lifecycle: `status` performs no writes and presents the repair as non-blocking pending work; `apply` reacquires and rechecks every required proof, publishes the repair through the existing lifecycle lock, transaction, rollback, and fresh post-commit verification, and reports the outcome like any other pending work.
- Safe Repair eligibility is **one exhaustive typed boundary**: every supported repair class — absent generated output, missing Installation Marker, missing repository-local exclusion section, and a provably missing Repository Exclusion Contribution — constructs its typed repair at its actual decision site and is classified through that boundary. Adding a class requires extending the boundary, so a repair can never surface through an ad-hoc inline branch. Each class keeps its existing evidence and presentation seam.
- Eligibility always requires independently proven live boundaries — an active Installation Receipt, a Marker whose identity matches, hash-proven owned roots, a live Project, untracked destinations, and a provable Git target — and the receipt must prove the exact write set. If any proof is absent, unsafe, unreadable, ambiguous, or would change user-managed bytes or repository ownership, the condition remains a Blocker and no write occurs.
- Surviving generated bytes are never an alternate ownership source. Agent Profile Kit does not reconstruct Installation State from generated output, silently adopt matching unowned output, overwrite drift, or automatically untrack repository paths.
- There is no general repair command. Concise output names the affected Project scope and resulting repair without teaching repository-exclusion internals; verbose and JSON retain the exact repair evidence.

A missing Repository Exclusion Contribution is the first condition delivered under this boundary through its own exhaustive class: when the proofs above hold and the target's owned section is absent or already contains exactly the recorded union plus the proven contribution, `status` classifies it as non-blocking pending work and `apply` records the contribution in the active receipt and publishes the resulting union through the ordinary transaction. Wrong targets, entry-set mismatches, stale desired write sets, tracked destinations, drift, missing identity proof, unsafe paths, and retirement-path divergence remain Blockers.

The maintained glossary (`CONTEXT.md`) owns the canonical Safe Repair definition; this record owns the decision and its rationale.
