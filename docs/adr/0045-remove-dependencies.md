# Remove Dependencies; Profile lists are the only source of what is installed

## Context

ADR-0001 introduced stable typed identities with optional dependency metadata:
Context Modules declared `dependencies` in frontmatter, Skills declared them in
an apkit-only `agent-profile-kit.yaml` sidecar, and the Installer resolved the
graph transitively, recording every inclusion reason in planning and the
desired-input digest. The format added apkit-only authoring work on top of
material users already have (#519 O1–O4, spec #593): every Context file needed
frontmatter, and a Skill needed an apkit-only file to compose. Inclusion
reasons also made the desired-input digest change when only a redundant
dependency edge changed, so receipts refreshed without any generated byte
moving.

## Decision

1. **Profile lists are the only source of what is installed.** A Profile's
   explicit `context` and `skills` lists are the complete desired artifact
   set. Transitive dependency resolution, cycle detection, catalog validation
   of dependency references, and dependency inclusion reasons are removed from
   ingestion, planning, and the desired-input digest (spec #593 DEC-006,
   ticket #596).
2. **The Skill sidecar is retired.** apkit no longer reads
   `agent-profile-kit.yaml`. A Skill package that contains it fails Workspace
   validation with that file's path and a fix naming the Profile's `context`
   and `skills` lists as the replacement (DEC-013: an earlier-release
   Workspace that becomes invalid is reported with the change needed). The
   package projector no longer carries sidecar-omission logic, because a
   package containing a sidecar can no longer reach planning.
3. **Context Module frontmatter `dependencies` is tolerated but never read.**
   The key stops being required and its value is unvalidated; it has no
   effect on what is installed. The key is not reported as a violation:
   spec #593 DEC-005 removes frontmatter reading for Context entirely
   (#600), so treating it as inert avoids churn that #600 would immediately
   supersede, while DEC-013's change-list duty is carried by the violations it
   names (sidecars, invocation keys, Profile `id`).
   (Completed by #600: all Context frontmatter is now inert
   delivered-as-written bytes; see ADR-0048.)
4. **This supersedes part of ADR-0001.** ADR-0001's dependency metadata
   (optional `agent-profile-kit.yaml` and typed dependency references) is
   superseded; ADR-0001's typed artifact identities and portable-artifacts-as-
   canonical-source principle stand. The Dependency term is retired from
   CONTEXT.md, and living documents no longer describe dependency resolution.
5. **Installation State compatibility is unchanged in shape.** Receipts never
   persisted reasons; they carry only the desired-input digest. Digests
   computed by earlier releases that included dependency semantics no longer
   match, which is the existing receipt-proven source-change path: `update`
   refreshes, keeping the installation identity and recorded output paths, and
   `uninstall` is digest-independent. Compatibility is proven by fixtures
   produced from the 0.204.0 commit (TEST-010).

## Consequences

- A Profile installs exactly the Context Modules and Skills it lists and
  nothing else, for every Host.
- Leftover sidecars are one validation violation each, with path and fix;
  authoring scaffolds no longer emit `dependencies: []`.
- The desired-input digest covers Profile selection and artifact content
  only, so a redundant-edge change can no longer force a Manifest refresh.
- Profiles that used Dependencies are repaired by listing their resolved
  artifacts in the Profile; validation names the sidecars to delete.
