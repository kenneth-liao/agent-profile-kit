# Explain the source of generated instructions and configuration

Generated material now says that it is generated and where lasting edits belong
(spec #491, US-021, DEC-014; ticket #503). US-021 supersedes US-010 and extends
its Skill and Context requirement to comment-capable generated Host
configuration; DEC-014 replaces DEC-010, and TEST-013 replaces TEST-008. Until
this record the product's ownership model lived only in the CLI, so a person
opening a generated file in an editor learned that it is disposable by losing an
edit (the independent review's S2 finding, captured by spec #491).

## Decision

- **One notice policy, rendered once per format.** `adapters/generated-notice.ts`
  is the single home of the notice: `Generated by apkit.`, the source guidance
  `Make lasting edits in the Workspace (apkit open).`, and
  `Replacing or removing independently changed files requires explicit consent
  in install, update, and uninstall.` Each projection renders those sentences in the comment syntax its
  format accepts — a Markdown HTML comment for Skill entry documents and
  composed Context, JSONC `//` line comments for the claimed OpenCode
  configuration. No projection authors its own wording, so the policy cannot
  drift between surfaces.
- **Every installed Skill entry document and Antigravity Context rule carries
  the notice as the first body line after frontmatter.** Frontmatter stays first, so Skill metadata, Agent
  Skills validity, and Host consumption are unchanged, and a
  disabled-invocation Skill keeps its generated top-level restriction together
  with the explanatory YAML comments already placed on those fields. The notice
  reaches every Skill-producing Adapter: the qualified shared projector that
  Codex, Pi, Antigravity, and OpenCode consume, Claude's Host-native
  `.claude/skills` projection, and Grok's `.grok/skills` projection. Supporting
  package members keep their bytes and modes, the Agent Profile Kit sidecar is
  still omitted, the Codex policy file is still copied unchanged when it already
  agrees, and qualified shared consumers still produce byte-identical packages.
- **Composed Context output carries the same notice in its envelope header**,
  directly after the Profile heading. That header is the one shared composition
  boundary every complete-envelope Host Adapter consumes, so Codex, Claude,
  Grok, OpenCode, Pi, and Antigravity rule zero all carry it without
  Host-specific wording. Antigravity's separate always-on per-module rules carry
  the same notice as the first line of their body, before the module boundary
  marker, so every generated rule explains itself rather than only the envelope
  rule that shares its directory.
- **Comment-capable generated Host configuration carries the notice plus
  Adapter-authored source-location guidance.** OpenCode's claimed
  `.opencode/opencode.jsonc` is the only such file today. Its notice names the
  project configuration files the generator does not claim
  (`opencode.json`, `.opencode/opencode.json`) and states that project-specific
  settings stay in the Project rather than in personal or global OpenCode
  configuration. That alternative-location list is the Adapter's Host fact and
  is also consumed by the occupied-configuration remedy wording, so the two
  surfaces cannot disagree. `.codex/hooks.json` is generated Host configuration
  but is strict JSON whose parser rejects comments, so it stays comment-free —
  the criterion is comment-capable configuration, and a notice there would break
  Host parsing.
- **The notice changes no ownership, parsing, or protection fact.** Whole-file
  ownership (ADR-0021) is unchanged: the notice grants no ownership, merges no
  user keys, and changes no unrelated user-owned configuration. It adds no
  projection requirement and no Blocker, so the configuration file is still
  proven by receipt hash, removed on uninstall, and blocked as a whole when the
  slot is already occupied. Skill frontmatter remains valid YAML and the JSONC
  document still parses as OpenCode's format after the leading comment block. An
  unedited generated file still updates without a prompt; only an independently
  changed file needs explicit consent (ADR-0032), which is exactly what the
  notice says. The consent sentence names `install`, `update`, and `uninstall`
  because that gate belongs to them: a Temporary Profile Installation is
  intentionally disposable and is removed only by its own explicit
  `machine remove-temp` teardown command, which discards drift inside its
  recorded roots without a changed-file consent flag (ADR-0015). Scoping the
  sentence keeps it true for temporary output without giving that surface a
  second notice or a second projection shape.

## Consequences

- Every existing installation gains the notice on its next successful update,
  because the projected bytes of an installed Skill entry document and Context
  envelope change. Generated output is disposable and refreshable drift, so no
  ownership is revoked and no Blocker is raised.
- A person reading an installed file — or a model loading it — learns where the
  lasting edit belongs without running a command first.
- The notice spends bytes, including inside Antigravity's 12,000-character rule
  limit, so a Context Module that previously fitted within roughly 200
  characters of that limit can now be refused. The refusal names the actual
  size and the limit, and content is still never truncated.
- The CLI surface itself is unchanged, so `docs/USER-JOURNEY.md` needs no stage
  or outcome change; the user-facing fact lives in the generated files and in
  `docs/guides/workspace.md`, which states it where generated output is
  described.
- Verification is a projection-level policy test plus the lifecycle suites that
  already pin generated bytes: notices appear in the body and after frontmatter,
  JSONC bodies parse unchanged, supporting resources and modes are preserved,
  and the qualified shared consumers stay byte-identical.
