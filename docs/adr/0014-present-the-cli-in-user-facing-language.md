# Present the CLI in user-facing language

Agent Profile Kit is built to be adopted by people who have never used it, so its default output is written for a newcomer completing a task rather than for a maintainer reading the domain model. Canonical domain vocabulary remains correct and unchanged in code, schemas, Installation Manifests, ADRs, and the issue tracker; what changes is that the default CLI view is no longer obliged to speak it. The design target is that a first run succeeds knowing only **Workspace**, **Profile**, **Project**, **Host**, and the rule that Agent Profile Kit owns what it generates. Any other term appearing in default output must justify its presence. `docs/USER-JOURNEY.md` holds the journey map, the gap register these decisions answer, and the accepted presentation principles.

**Vocabulary layering.** `CONTEXT.md` stays the single canonical home for what a concept *is*; a UI lexicon owns how that concept is *rendered* to a user. These are different facts — definition versus presentation — so this is a layer, not a second home, and the mapping is one-directional. A test asserts that internal-only terms (`Profile Installation`, `generated-output`, `Repository Exclusion`, `Installer-owned`, `reconcile`, `Artifact ID`) do not appear in default-view strings, making the boundary structural rather than a review obligation.

**Information design.** Default views show objects rather than counts of abstractions: generated files are listed as paths with `+`/`~`/`-` markers, capped with overflow deferred to `--verbose`. Repository Exclusions collapse from a titled block to one clause, with deltas available under `--verbose`. The Hosts a user selected at `bind` are echoed wherever their output is described. Blocked runs lead with the blocker and demote plan detail that cannot happen. Ownership is taught at the moment it becomes load-bearing — when output has been hand-edited — instead of through a per-run explanations block, and the drift blocker states its remedy explicitly.

**Host Setup Steps.** Adapters return structured, typed post-apply requirements alongside their file plans (`approval-required`, `trust-required`, `launch-constraint`, `shared-path`), preserving ADR-0002's rule that Host knowledge never leaks into shared layers. `apply` renders all of them, `preview` renders only `approval-required` and `launch-constraint`, and `status` surfaces one Host-level callout rather than repeating per installation. This closes a silent-failure class: a Codex user who declines the generated `SessionStart` hook otherwise gets an installation reporting `current` while Context never loads, and a Grok user co-bound with Claude otherwise finds no `.grok/rules/` file and reasonably concludes the install failed. The name avoids `Activation`, which `CONTEXT.md` already defines as what starts a Skill.

*Amendment ([#202](https://github.com/kenneth-liao/agent-profile-kit/issues/202)): every Host Setup Step now carries `transition` or `standing` provenance classified at the Adapter boundary. `preview` presents transition-triggered steps only when the plan changes their associated output, `apply` presents change-relevant transition steps plus a separate compact standing reminder, and `status` retains the standing reminder without replaying transition setup. See `docs/ARCHITECTURE.md` (Adapter Boundary) for the current rendering rules.*

**Command name.** The published command becomes `apkit`. The product name, the npm package, and every generated path — `.agent-profile-kit/`, `.claude/rules/agent-profile-kit.md`, `~/.agents/agent-profile-kit/`, and the `# BEGIN Agent Profile Kit generated paths` exclusion markers — remain `agent-profile-kit`, because those strings are the ownership contract that Installation Manifests, hashes, and Markers prove against. Renaming them would fail every existing installation's ownership proof and strand users in the drift dead end this work exists to remove.

An Installation Manifest's `engine_version` records the engine that last published it; it is provenance, not desired state and therefore not an independent reconciliation trigger. Actual desired-state inputs — source hashes, Adapter and Host versions, selected Hosts, and normalized outputs — continue to trigger reconciliation. This lets a packaging-only command rename and version bump leave an otherwise-current Profile Installation byte-identical, while the recorded engine version still advances whenever a real reconciliation change publishes a new Manifest.

**Machine surface.** A `--json` mode is added so automation depends on a stable contract and the human view stays free to improve. Exit codes become uniform across `status`, `preview`, and `apply`: `0` clean, `1` tool error, `2` blockers present. `status` returning `0` while reporting blockers is not preserved.

**Teaching surface.** Per-command `--help` carries purpose, syntax, worked examples, what the command writes, and what to run next. `guide <topic>` gives short format answers in place of only a 621-line document, and `init` scaffolds a bindable example Profile so a first end-to-end run is available immediately. Help examples, `guide` examples, and scaffolded files derive from one canonical example set that CI binds and applies, extending the existing `COMMANDS`-table pattern so documented examples cannot rot.

**Versioning.** Until 1.0 the repository follows standard SemVer 0.x: breaking changes bump the minor version and never force a premature 1.0. Breaking changes are expected while the tool iterates toward its first public release, and no compatibility shims are carried for pre-1.0 behavior.
